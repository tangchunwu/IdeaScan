# IdeaScan 需求验证与优质需求发现优化建议

日期：2026-11-04。审查基线：`5c3463c`，本地工作目录 `/private/tmp/ideascan-validation-run`。

本次检查真实源码、既有产品研究和项目复盘，并对三个纯函数行为做离线复现。没有调用付费供应商，没有执行线上登录态验收，没有修改业务代码。以下“当前行为”是本地代码事实；“建议”是待实施方案。

## 1. 产品目标与结论

两个模块应分别回答：

- **寻找优质需求**：在哪个市场、什么人、什么具体时刻，有一个值得进一步研究的小应用机会？为什么现在值得看？
- **需求验证**：这一个机会，目前哪些假设有证据、哪些被反驳、哪些还未知？下一笔验证投入应该花在哪里？

当前渠道覆盖已增加，但决定质量的主要瓶颈是证据进入分析的方式、地域检索、结论口径和两模块交接。优先修复可信度，再增强发现能力，再积累验证反馈。

针对本项目的定位，优质机会还应保留“有趣、地域适配、能做成小软件”的特征。情绪安慰、仪式感、被关心、纪念和社交表达都可以产生价值，不必一律改写成工作效率问题；同样不能仅凭文化流行就推定付费需求。

## 2. 需求验证：已确认的质量断点

### 2.1 评论被采集，却没有进入当前正常评分链路

证据：[`validate-idea-stream/index.ts`](../supabase/functions/validate-idea-stream/index.ts)，`socialItems` 约第 1706 行，最终分析 prompt 约第 2561 行；[`summarizer.ts`](../supabase/functions/_shared/summarizer.ts)。

当前 L1 从 `sampleNotes` 取帖子标题/正文，从竞品结果取网页内容；L2 聚合这些摘要。最终分析 prompt 使用市场洞察、竞品洞察、关键发现和内容数量/平均赞数，没有传入 `sampleComments` 原文。即使正常链路抓到了很好的“正在付费但不好用”评论，最终分析也未必看到它。

**建议**：先构造“父帖＋评论”的证据组，给每条原文稳定 evidence ID；提取场景、现有做法、付出、问题和态度，再带 ID 聚合。关键主张必须能回到原文。情感比例只能来自实际分类，不由模型凭整体印象填写。

验收：固定帖子正文，替换为两组相反评论后，相关主张必须改变或明确冲突；不能仅展示了评论就算评论已参与分析。

### 2.2 模型失败后仍能得到“真实需求”标签

证据：`buildGroundedFallbackAnalysis` 约第 2715 行；[`DemandDecisionCard.tsx`](../src/components/report/DemandDecisionCard.tsx) 约第 54 行。

离线复现：模型失败，输入 `totalNotes=40`、12 条“好看，哈哈”评论、5 条含 snippet 的网页、没有识别竞品，返回 **78 分**，结论建议进入小范围 MVP。评论语义根本未被该规则读取。前端 `score >= 70` 就显示“真实需求”。零样本时规则仍返回 35 分及固定情感比例。

这只能证明规则依赖数据数量，不能证明线上的某个具体报告已经误判。

**建议**：模型失败时保留采集结果，状态为“分析未完成，可继续分析”；缺证据时用“证据不足”。不为维持报告完整而生成需求分、市场规模、情感比例。判断状态优先使用“值得小测 / 需缩小人群 / 暂缓 / 证据不足”。即使保留分数，也仅作为研究排序，并独立展示依据和覆盖缺口。

验收：模型失败、全空样本、只有竞品营销页、只有娱乐互动时，均不能被规则自动提升成“真实需求”。

### 2.3 报告缺字段时会补出没有测量依据的数据

证据：[`useReportData.ts`](../src/components/report/useReportData.ts) 约第 57、76、101、155 行。

离线调用空报告：市场规模显示“中等规模”，竞争程度“中等”，趋势“平稳”；周趋势补为 85、92、100、95、110、125、115；情感补为 33/34/33，六个维度默认 50 分。`positive || 33` 还会把合法的 0% 替换成 33%。

此外，[`base-adapter.ts`](../supabase/functions/_shared/channels/base-adapter.ts) 将采到的帖子数乘 100 作为估算总量，生成固定周分布。这些估算不应作为真实市场规模、总互动或趋势。

**建议**：未知字段保持 `null/unknown`，图表无真实时间序列就显示“暂无趋势数据”；明确区分已采帖子数、评论数、独立原帖数、作者数和供应商估算总量。陈旧报告缺字段不能补成新事实。

验收：空报告不产生数字图表；0% 保持 0%；相同采集数据不因启用更多平台就膨胀成更大的市场。

### 2.4 海外平台接上了，市场上下文没有完整贯通

证据：验证函数约第 1534 行仍向海外适配器传 `xhsSearchTerm`；`expandKeywordsSimple` 约第 2122 行实际是字符串拆分，并非语义扩词；`searchCompetitorsSimple` 内 Bocha 固定 `zh-CN/zh`，You 固定 `country=CN`。竞品深搜也使用中文“定价 价格”“用户评价 口碑”。TikTok 适配器固定 `region: US`。

不能因此说所有海外结果都无效：Tavily 等仍可能返回海外页面。但当前选择日本/韩国不等于执行了日语/韩语市场研究。

**建议**：引入共享 `MarketContext`：国家码、研究语言、目标人群、具体场景、时间范围、平台。针对目标语言生成问题词、替代方案词、竞品词和反证词。国家、语言、作者所在地是三个不同维度，来源所在地缺失时明确未知。

### 2.5 样本选择和缓存还可能改变研究对象

证据：[`context-budgeter.ts`](../supabase/functions/_shared/context-budgeter.ts) 按赞数、评论数、长度、新鲜度排序；深度模式压缩到 12 帖/24 评论，L1 再只用前 8 帖。验证缓存调用只传 `p_keyword`；仓库中对应迁移按关键词模糊匹配，不含国家/语言/平台集合。

**建议**：原始证据、清洗后的全集、模型上下文样本分开保存；按相关性、具体行为、地域匹配和来源多样性分层取样，保证低赞但高价值的原文进入分析。缓存键包含市场、语言、平台、意图、时间窗与协议版本；复用时再次校验覆盖范围，记录采集时间而非假定新鲜。

线上 RPC 是否与仓库迁移一致，仍需只读核对后才能判断实际影响范围。

## 3. 优质需求发现：从一次搜索升级为问题发现

### 3.1 当前做到了什么

[`opportunity-discover/core.ts`](../supabase/functions/opportunity-discover/core.ts) 已经约束来源 ID、至少两条原文来源、候选为假设、证据不足少返回。源链接过滤、取消后的迟到响应隔离和账号边界值得保留。

但目前主要流程是：国家＋行业＋可选关键词 → 单轮采集 → 一次模型分析 → 最多五个候选。深度模式主要增加样本量，不会对候选进行第二轮验证。来源正文主要使用搜索片段；网页原文没有进一步抓取。

### 3.2 入口增加“想找哪类小应用”

行业之外，支持可选的机会类型：

| 机会类型 | 观察对象 | 要找的行为信号 |
| --- | --- | --- |
| 安心与风险接住 | 独居、报平安、重要事项遗漏 | 主动确认、重复检查、找人兜底 |
| 情绪与仪式 | 许愿、祈祷、纪念、日常鼓励 | 重复使用、私密记录、主动分享、现有付费 |
| 地域节日任务 | 黑五、演出远征、节庆准备 | 价格损失、时间压力、协同和信息遗漏 |
| 兴趣收藏与关系 | 小卡、宠物、兴趣社群 | 记账、交换、清单、共同维护、纪念产物 |
| 日常小麻烦 | 临时决策、记忆、沟通 | 截图/表格/群消息等真实替代方案 |

可以另外输入独立开发者约束：个人/小团队可做、软件交付、目标价位、是否接受季节性、是否依赖高成本人工服务。不要把所有情绪需求都过滤成“没有效率价值”。

### 3.3 用本地说法搜“经历”，而非重复搜产品名

当前 [`sources.ts`](../supabase/functions/opportunity-discover/sources.ts) 拼接长查询，并在全网追加“手工 低效 替代”或 `manual workflow pain points alternatives`。这种意图有用，但偏向效率工具，也容易搜到面向创业者的观点文章。

建议按意图生成有限查询组：具体经历、重复任务/仪式、现有替代、付款、放弃原因。以下是**待执行示例**：

- 美国黑五：`price dropped after I bought`、`missed return window`，再找商家实际价格保护规则和现有工具收费。
- 日本远征：`遠征 立替 精算 面倒`、`推し活 友達 お金`，再核实真实协同过程和当地应用评价。
- 韩国愿望仪式：用本地语言查重复使用、分享和订阅体验，同时查“看完一次就不用了”的反证。

每个平台适配自身查询长度和排序。不要每条查询强塞英文国家名；优先用语言、当地社区/话题和供应商确实支持的地域参数，并承认地域不可验证的边界。

### 3.4 先抽取需求信号，再聚类成机会

每条原文建议抽取：谁、何时、想完成什么、现在怎么做、遇到什么阻碍、时间/钱/情绪成本、是否复发、是否为替代方案付费、地域与时间依据、原文引句。

信号分类至少区分：体验描述、实际求助、重复做法、已付费、明确购买意向、娱乐互动、商业推广。它们可以共存，不能按负面情绪多少直接推算需求强度。

随后按“同一人群＋同一触发场景＋同一任务”聚类。例如同样是宠物话题，日常照护、走失和纪念不应混为一个宠物 App。跨国结果也不要直接合并为已验证的全球需求。

### 3.5 给入围候选做一次专门复核

对少量入围方向追加：

1. 本地用户原话：真的在描述问题/价值，还是表达文化兴趣？
2. 替代做法：已经用免费工具、亲友帮助、纸笔或表格解决到什么程度？
3. 竞品与价格：付费入口、货币、一次性/订阅、核实日期和链接。
4. 反证：免费方案够用、低复用、隐私顾虑、无法触达用户、季节已过等。
5. 小软件适配：首版能否独立交付，最小结果是什么，首个付费人是谁？

只有抓取到了对应原文，才写“定价已核实”。第三方收入估算、创始人自述、App 标价和真实支付必须分开。不能用付费竞品存在推导本候选必然有人付费。

### 3.6 机会卡用于比较和行动

建议默认展示：

- 具体场景与用户原话；
- 为什么值得看，以及地域/节日/趣味表达如何帮助使用与分发；
- 问题强度、复发频率、现有花费、来源可信度、获客可达性、小应用可交付性；
- 最强支持证据、最强反证、最大未知；
- 一个首版切口和一个最小验证动作。

不要用另一个未经校准的单一总分替代比较。可以提供“值得小测 / 需要重构 / 暂缓 / 证据不足”分组，并展示理由。最终希望挑十个方向时，可以分批扩展覆盖面后收敛；单轮证据不足不能为凑十个补造需求。

## 4. 两模块统一为同一份证据档案

现在商机雷达进入验证仅通过 URL 回填标题、痛点、国家、行业、平台，不会交接来源池、引句或反证。验证会重新检索，容易丢失此前最有价值的证据。

建议让两个入口共用：

`研究范围 → 查询计划 → 原始证据 → 需求信号 → 候选假设 → 支持与反证 → 验证动作 → 行为结果`

- 同一条机会有稳定 ID，验证从已有证据继续补洞。
- 记录证据沿袭、时间范围和新增调用，旧证据不足时定向补采，不直接照搬旧结论。
- 分享 URL 不塞密钥、用户原文和整份证据；使用具备账号归属校验的研究记录。
- 原始证据与模型推断分层存储，保留版本和模型信息以便复核。
- 复用既有报告 JSON 与现有表的可行部分；持久机会库若需要新表/索引/RLS，应单独设计迁移和权限验收，不能假定当前已支持。

已有 `Discover` / `HunterSection` 还存在另一套机会展示与 `auto=true` 跳转；`signal-processor` 使用另一套机会分。建议逐步统一入口名称、机会卡、证据规则和手动启动语义，避免三个页面给出不同“优质需求”标准。

## 5. 采集可靠性与成本要服务研究质量

- 平台搜索成功、单帖评论失败应保留已经获得的帖子和评论，记录阶段失败，不让一个评论异常清空整个平台。当前多个海外适配器的外层 catch 会返回空结果。
- Threads 适配器把 `code` 优先当 `post_id`，而官方评论参数需要数字 post ID；应把 API ID 与展示 shortcode 分开。该问题来自静态合同检查，尚未用真实接口复现。
- X 的 `x.com/twitter.com`、Threads 的域名别名应统一原帖键。同一作者、转载和跨平台重复内容也要检查，不能只数 URL。
- 多平台固定总证据池时按相关性和覆盖分配，避免前面填满后其他信源进入不了分析。
- 快速模式做候选初筛，深入模式对入围候选定向补证；按物理请求数、超时、取消和费用预算限制采集，不能为了凑样本无限换词。
- 付费意图按钮、提交联系方式、开始结账和实际支付分别计量。实际支付需来自可核验的订单/支付回调。现有实验模块可以继续复用，但本次没有审计线上事件完整性和支付真实性。

## 6. 建议实施顺序

| 阶段 | 必须交付 | 主要范围 | 通过条件 |
| --- | --- | --- | --- |
| P0：可信度修复 | 评论进分析；未知不补数字；失败不输出需求判定；统一样本口径；保留部分采集结果；修正平台 ID/去重 | 验证流、摘要、报告数据层、海外适配器、雷达去重 | 空样本、模型失败、娱乐互动、重复链接均不产生已验证结论；原文可追溯 |
| P1：发现质量 | 共享市场上下文；本地语言查询；机会类型；信号抽取与聚类；对入围候选补付费证据和反证 | 雷达采集/核心逻辑、验证检索、前端范围设置 | 选日本能看到实际日语查询；每个入围方向可说明支持/反证/未知，地域缺失不冒充已核实 |
| P2：研究闭环 | 带证据进入验证；机会保存、比较、继续研究；访谈/报价/使用/购买结果回写 | 研究记录、权限、两入口联动、实验模块 | 刷新不丢研究；重复验证只补证据缺口；可追踪一个机会从线索到行为结果 |

## 7. 如何判断优化有效

建立一小批经人工标注的固定研究样本，覆盖强工具需求、文化兴趣、情绪价值、广告、反证、地域错配、零数据、供应商失败与节日过期。让两个模块使用相同样本比较改前改后行为。

重点指标：

1. **错误高置信结论数**：模型失败或证据不足时仍给“真实需求”的次数，应为零。
2. **关键主张可追溯率**：支持/反证是否引用真实存在且相关的原文，不只检查 ID 合法。
3. **目标市场有效证据率**：单独标注语言匹配和地域依据；未知不进入“地域已证实”分母。
4. **有效机会比例**：人工复核后认为人群、场景、已有替代和切口均清晰的候选比例。
5. **单位成本和重复调用**：每个有效候选实际调用量、失败量、时间；高质量改进不能只靠无限增加请求。
6. **研究后的真实行动**：继续研究、访谈、报价、原型使用、复用和购买分别记录；导出报告不等于需求验证成功。

这些是建议度量项。本次没有取得线上基线或做转化实验，也不设定伪装成行业标准的达标率。

## 8. 本次结论适用范围

审查对象是本地已推送基线的实现，不代表生产已部署相同代码。离线复现只证明函数对给定输入的行为，不代表真实平台用户的需求。未新增付费 API 调用，未修改业务代码、数据库或上线配置。下一轮应先实施 P0，再用固定样本和有限真实采集验收。
